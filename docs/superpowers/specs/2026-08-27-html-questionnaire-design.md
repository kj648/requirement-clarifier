# 设计：HTML 可交互确认单

> 日期 2026-08-27 · 状态：待评审 · 原型 `docs/superpowers/specs/2026-08-27-html-questionnaire-prototype.html`

## 1. 问题

现在阶段二产出的确认单是 Markdown（`templates/questionnaire-template.md`）。填写人是业务方——财务、运营、提需求业务——**他们不认识 Markdown**。实际后果：

- `☐` 打勾要手改文本，业务不会，回来的常是微信语音或一段散文，格式契约当场失效，`check_questionnaire.py` 无从下手；
- 题目间的依赖只能写成散文注释（"若第 1 题选 A，第 3、4 题可跳过"），业务会照着答一堆作废的题；
- 举例数字（跨分支数值对照表）是静态表格，业务看不出"我选的这个对应哪个数"；
- 第一部分「已确认事项核对」用一个全局「全部无异议」复选框，与"下面还能补充异议"自相矛盾；
- 每题的依据（哪句原话、哪行代码）不在单子上，业务无法判断这题是真漏洞还是 AI 臆想的场景。

## 2. 目标 / 非目标

**目标**

1. 业务在浏览器里点选即可完成填写，零 Markdown 知识；
2. 题目依赖可执行（选 A 就没有 A1），跳过留痕而非留空；
3. 每题挂可追溯的依据，无据的题公开标红并可被业务一键证伪；
4. 导出一份**可归档、可机检**的回执，`check_questionnaire.py` 现有契约不破；
5. 一份单子的题散在多拨人手里时，每人只先看自己那部分。

**非目标**

- 不做后端、不做账号、不做在线协同。单文件 HTML，双击可开，可离线，可内网，可打印。
- 不做 Artifact 托管（业务常常打不开 claude.ai 链接；skill 分发给别人时也不保证该能力可用）。
- 不替业务拍板：不做跨题自动预选口径选项（见 §8 拒绝清单）。

## 3. 已拍板的决定

| # | 决定 | 理由 |
|---|---|---|
| D1 | 单文件 HTML + 导出回执文件 | 零依赖、可离线内网、回执天然可归档进 `raw/` |
| D2 | `questionnaire.json` 题目数据 + 固定 `questionnaire.html` 模板 + build 脚本 | 交互写一次全项目复用；依赖关系与出题纪律变成可机检的声明式字段 |
| D3 | 分组平铺 + 条件折叠（非逐题向导） | 题散在多拨人手里，必须允许跳着答、允许转交；平铺还能让业务预估工作量 |
| D4 | 主问用勾选，子问回填进【作答区】 | 现有 checker 把同题多勾判为多选 WARN；这样零改脚本。子问的结构化副本放机读 JSON |
| D5 | 回执 = 人读 Markdown + 末尾压缩 JSON 机读区 | 人看 md、AI 读 JSON、现有机检吃 md |
| D6 | 第一部分逐条三态核对（对／不对／未表态），取消全局「无异议」 | 全局勾与"可补充异议"自相矛盾；"无异议"应是结论而非前置动作 |
| D7 | 每题挂三档依据：`原话` / `代码` / `无据·请证伪` | 沿用仓库既有证据纪律；证据越弱越显眼（无据默认展开） |
| D8 | 无据的题照样出，但强制标红 + 给证伪出口 | 盲区清单的价值就在问出没人想过的场景；靠公开标记与一键证伪控幻觉，而非禁止提问 |
| D9 | 落款：日期自动（导出时间），填写人可留空 | 手填日期不可靠；浏览器沙箱拿不到操作系统用户名（无此 API），改用预填 + localStorage 记忆 |
| D10 | 未署名不拦导出，改为**自动降级标签** | 业务常需先交一半再转交；纪律靠回执自带降级声明落实，不靠禁用按钮 |
| D11 | 导出预览是人读回执，Markdown 折叠为技术细节 | 业务不懂 Markdown 正是本次改造的起点，预览不该甩源码 |
| D12 | 按建议回答人分区（身份选择器），不锁死 | 借 `to-questionnaire`「先定收件人」；现实中常有人代填，故只折叠不禁止 |
| D13 | 分支穷举是出题者的义务，不靠交互补救 | 通路是一次性发单、异步回填，中间没有 AI，无法答完一题再想下一题（§6） |
| D14 | 每道主问由模板自动追加「都不是」兜底出口 | 同上：选项集猜错时业务当场没法跟 AI 说，不能逼人在错选项里勉强挑一个 |

## 5. questionnaire.json 契约

顶层声明角色表——**回答人必须是 id 引用，不得是自由文本**。原型里 `财务` 与 `财务 AR 负责人`、`财务 拍板人` 被算成三个人，一份单子分裂出幽灵收件人。

```json
{
  "doc": {"id":"AR-KPI","title":"AR 回款 KPI 报表","round":1,
          "sent_by":"开发 KJ","sent_on":"2026-08-26","due_days":3,
          "usage":"您的答案会写进开发规格并落库存档，日后报表算错时按这份回执追溯"},
  "roles": [{"id":"fin_ar","name":"财务 AR 负责人"},
            {"id":"fin_owner","name":"财务 拍板人"},
            {"id":"ops","name":"运营"},
            {"id":"biz","name":"提需求业务"}],
  "part1": [{"n":1,"we_understand":"…","note":"是否还要按周或季度？"}],
  "layers": [{"n":1,"why":"决定其余 8 个指标怎么算"}, {"n":2}],
  "questions": [
    {
      "no": 1, "layer": 1, "blocking": true,
      "title": "什么叫「到期」？",
      "who": ["fin_ar"],
      "background": "系统里只有开了票的应收才有到期日（开票日 + 账期）…",
      "advice_allowed": false,
      "evidence": {
        "tier": "code",
        "cites": [
          {"kind":"src","path":"docs/requirements/raw/2026-08-20-财务口述.md","line":12,
           "snippet":"开了票才有到期日，没开票的只有个预估收款时间"},
          {"kind":"code","path":"app/models/receivable.py","line":41,
           "snippet":"due_date = invoice_date + payment_term_days"}
        ],
        "weak": "子问「已开票但没填账期」无据：只据字段可空推断，未在库里核过这种数据存在"
      },
      "groups": [
        {"id":"main","options":[
          {"key":"A","label":"只算已开票的应收，按「开票日 + 账期」到期","cost":"和现在待回款页面一样"},
          {"key":"B","label":"没开票的也算：按「预估收款时间」到期","cost":"覆盖全，但两种日期混在一起"},
          {"key":"C","label":"没开票的单独出一个数，不混进其他指标"}]},
        {"id":"term_null","ask":"已开票但没填账期的应收怎么算","tier":"guess","inline":true,
         "options":[
          {"key":"A1","label":"当作未到期"},
          {"key":"A2","label":"单列「无到期日」，不进比率"},
          {"key":"A3","label":"当作开票当天到期"},
          {"key":"nil","kind":"nonexistent","label":"这种情况不存在：已开票必有账期"}]}
      ],
      "demo": {"given":"8 月到期已开票 100 万、收回 70 万；未开票预估 40 万；无账期 10 万",
               "rows":[{"when":["A","A1"],"k":"总到期回款率","v":"70.0 %"},
                       {"when":["A","A3"],"k":"总到期回款率","v":"63.6 %"},
                       {"when":["B"],    "k":"总到期回款率","v":"50.0 %"}]},
      "reveal": [{"when":"C","ask":"这个单独的数放在报表哪里、给谁看"}]
    }
  ],
  "links": {
    "na":    [{"when":"1=B","target":"7.term_null","note":"按预估收款时间判到期，不看账期"}],
    "carry": [{"from":"7.crm_field","to":"10.crm_field","kind":"fact"}],
    "clash": [{"when":"4=B & 1=B","why":"锁账锁不住可随时改的预估收款时间","require_explain":true}]
  }
}
```

**字段语义要点**

- `advice_allowed: false` 把"规则／账务口径题永不标建议选项"从口头纪律变成**结构约束**——模板对这类题不渲染「开发建议」位，写了也渲染不出来。
- `evidence.tier`：`src` 原话（绿）／`code` 代码（蓝）／`guess` 无据（红，依据区默认展开）。`cites` 转成 `> 证据: <path>:<line> | "<snippet>"` 交 `verify_evidence.py` 校验。
- `options[].kind: "nonexistent"` 是"这种情况不存在"的出口，与"我不清楚"台阶并列。
- `groups[].tier` 允许**子问单独标无据**，不必整题降档。
- `layer` 是**依赖层级**，见 §6。注意与 `doc.round`（第 N 轮确认单）是两个概念，不要混用 round。
- 兜底出口 `kind:"other"` 由模板自动追加到每道主问，**出题者不需要写**。

**条件表达式** `when`：支持 `&`（与）、`|`（或）、`!=`、`in [a,b]`。刻意不做成表达式语言——超出这四种的依赖说明题目该拆。

## 6. 依赖分层（借 grilling 的前沿模型，但执行者换成页面）

**先说清一处差异。** `grilling` 的前沿模型假设 **AI 在回合之间**：问一轮 → 用户答 → AI 重算前沿 → 再问下一轮。本 skill 的通路是**一次性发单、业务异步回填、一次性收回**，中间没有 AI。照搬"分轮问"是错的。

能借的是**拓扑分层本身**，执行者从 AI 换成**模板运行时**：

- 出题时按依赖拓扑给每题标 `layer`：一道题的答案依赖另一道未答的题，它属于更深的层。
- **一次性全发**。深层的题灰着但可见（业务仍能预估工作量），标「等问题 1、2 定了才有意义」；前置一答完，页面当场解锁或剪掉。
- 也就是说：`reveal` / `links.na` 就是**离线版的前沿推进**，只不过发生在浏览器里，不需要 AI 参与。

### 由此长出的两条硬约束

**① 分支穷举是出题者的义务。** 页面只能执行出题时**已声明**的依赖；AI 无法在业务答完第 1 题后临时想出一道新题。选 A 的下游、选 B 的下游都得预先写进 json。漏掉的分支只能等下一轮确认单（skill 已有的多轮机制），补救成本是一整轮往返。

**② 每题必须有兜底出口。** 选项集猜错了，业务当场没法跟 AI 说。模板给每道主问自动追加一条 `⊕ 都不是——我要选的不在这几个里`，选中后展开自由文本「那实际是怎样？照实写，别在上面几个里勉强挑一个」。这是"无法逐题追问"这个约束的直接补偿，与 `⊘ 这题不成立`（场景不存在）和「我不清楚」（不归我管）并列，三者语义不同，都要有。

### 完成条件跟着改

不能是"前沿空了"——一次性发单时前沿永远不空（下游分支还没被选择）。改为两侧各一条：

- **出题侧（发单前可机检）**：**分支覆盖完整**——不存在"某个选项选下去掉进没题可问的空洞"。加上依赖闭环校验：`links` 与 `reveal` 里 `when` 引用的题必须存在，且 `layer` 严格小于被约束题的 `layer`；悬空引用或反向依赖 → FAIL。
- **收单侧（阶段三）**：回执里若出现出题时没预见的分支——有 `☒ 本题不成立`、有 `kind:"other"` 的作答、或有未说明的矛盾——即判定**需要下一轮**，而不是硬把答案合并进 spec。

**顺带一个后果**：`links.clash` 的地位因此更高。没有 AI 在中间把关，页面是**唯一**能在填写现场发现矛盾的东西——它不是"省一轮往返"的优化，而是这条通路上仅有的现场校验。

## 7. 页面行为规格

| 机制 | 行为 | 回执落痕 |
|---|---|---|
| **条件显隐** `reveal` | 选中触发项才展开子问；未触发不渲染 | 未展开的子问不出现 |
| **自动不适用** `links.na` | 前面的选择让后面某组题逻辑上不存在 → 该组灰掉盖说明层，不计入漏答 | `不适用（因问题 1 选了 B：…）`，**空白与不适用可区分** |
| **事实传播** `links.carry` | 前面填的事实（字段名、人名、天数）带到后面当默认值，字段变蓝并提示"沿用问题 7 填的「cust_type」，不对可以直接改"。目标空着、或还拿着上次自动值 → 可带；**业务一动手改过，永不再覆盖，上游改了也不动** | 正常作答，JSON 标 `carried:true` |
| **当场冲突** `links.clash` | 两个选择互相打架时红框当场弹出，要求二选一或写明处理；进度条同步计数 | 单独一段 `## ⚠ 填写时暴露的矛盾（请开发优先处理）`，带业务当场的解释 |
| **演示数字结算条** | 每道口径题下把跨分支数值对照表做成活的：选 A+A1 则 `70.0 %` 那行点亮 | 不落痕（仅辅助判断） |
| **兜底出口** | 每道主问末尾自动追加 `⊕ 都不是——我要选的不在这几个里`，选中展开自由文本 | `☑ 都不是（实际口径见作答区）` + `【作答区】实际的口径是：<原话>`；人读预览直接显示业务写的实话 |
| **题级证伪** | `⊘ 这题不成立：场景不存在，或问错了` → 整题灰掉，展开理由框 | `☒ 本题不成立（业务证伪）：<理由>`，主选项全部留空 |
| **身份分区** | 顶部「我是」选择器；选定后只亮属于该角色的题，其余折叠但可点标题展开自填 | `填写身份：财务 AR 负责人（本轮只对该身份名下的题负责…）` |
| **逐条核对** | 第一部分每条三态；选「不对」才展开该条说明 | 三列表 `# / 核对 / 说明` + 全「对」时才写"无异议" |
| **导出闸门** | 无闸门。未答／未核对／矛盾均只警告 | 回执头部「回执成色」行 + 未署名降级声明 |

`clash` 把冲突检测从阶段三（回执收回后由 AI 做）提前到**填写现场**——业务人还在，当场就能解释，省掉一整轮往返。

## 8. 借鉴与拒绝

调研对象：`mattpocock/skills` v1.2.3 的 `grill-me`、`grill-with-docs`、`codebase-design`，外加同仓的 `to-questionnaire`。`grill-me` / `grill-with-docs` 各仅 7 行薄壳，实现共享在 `grilling`（28 行）。

**采纳**

| 来源 | 借鉴 | 落点 |
|---|---|---|
| `grilling` | 设计树 + 拓扑分层（**前沿推进的执行者改为模板运行时**，不是 AI 回合） | §6 |
| `grilling` | **"Finding facts is your job, never the user's"** — 能从代码／数据／归档查到的事实一律不问业务；查不到才出题并标【假设·未取证】 | SKILL.md 阶段二**前置**纪律，接在 D8 之前 |
| `to-questionnaire` | **"Grill the send, not the subject"** — 先定收件人，题只瞄准收件人知识与我方需要之间的差集 | D12 身份分区；`roles` 顶层声明 |
| `to-questionnaire` | 抬头写明「你的答案会被用到哪里」 | `doc.usage` |
| `codebase-design` | Glossary 的 **Avoid 列表** → 禁用措辞表 | §9，`verify_evidence.py` 探测 |
| `codebase-design` | **Rejected framings** → spec 记「被否决的口径及理由」 | §9，HTML 零成本自动产出 |

**不适用：多轮交互本身。** `grilling` 的"问一轮 → 答 → 重算前沿 → 再问"依赖 AI 常驻回合。本 skill 的确认单是一次性发出、异步回填、一次性收回，中间没有 AI，故只借拓扑分层，不借回合节奏；代价由 §6 的分支穷举义务与兜底出口补偿。

**明确拒绝：每题给推荐答案**（`grilling` 的 `➡️ <recommended answer>`）。

`grilling` 对每题都给推荐答案，这是它最受欢迎的特性。但对象不同：`grilling` 面对**用户自己**（开发者），推荐答案是加速，答错自己担；本 skill 面对**第三方业务方**，推荐答案就是替他拍板——业务会一路点确认，把从没想过的账务口径签掉，日后一句"我没说过"，返工归开发。

这与现有纪律"规则／账务口径类问题永不标注建议选项"一致，且已由 `advice_allowed` 强制。纯偏好／成本敏感类题（格式、时点、入口位置）仍可标"开发建议"，这是原有分级，不变。

## 9. 对现有文件的逐条改动

**`scripts/check_questionnaire.py`**（新增三条规则）

1. 检测填写人为「未署名」→ WARN + 输出"须按【开发拟定·待追认】入账"。**当前缺口**：落款行写成 `填写人：（未署名·导出自 HTML 确认单）` 时字段非空，静默绕过原本"缺填写人 → FAIL"，纪律会无声烂掉。
2. 识别 `☒ 本题不成立` 为**业务证伪**并单独计数，不混入"已答"。现在它被算作普通已答，AI 会漏掉"这题该删"这个信号。
3. 检测 `## ⚠ 填写时暴露的矛盾` 段 → WARN；矛盾未附业务说明 → FAIL。**当前缺口**：回执带着未解决的矛盾，机检仍报"✓ 通过"。

**`scripts/verify_evidence.py`**

- 支持直接吃 `questionnaire.json`，逐条校验 `evidence.cites`。
- 新增**禁用措辞探测**：禁「用户希望／业务要求／据了解／应该是」，要求改为【业务确认·日期】／【开发拟定】／【假设·未取证】。原有"无证据支撑时禁用'业务明示／业务已确认'措辞"并入此表。
- **已知缺口**：`{"kind":"receipt"}` 这类非文件引用（如"引自本单第一部分您的回填"）无法校验。处置：要求回执先归档进 `raw/` 再改成真路径引用；未归档的一律按弱证据计。

**`SKILL.md` 阶段二**（出题纪律增补）

1. 出题前先自查事实，能查到的不问（借 `grilling`）；
2. 每题必挂三档依据，无据题标红并排同组最后；
3. 每题给证伪出口；
4. 依赖不再手写剪枝注释，改为 `layer` + `links` 声明；
4b. **分支穷举义务**：每个选项的下游分支必须在本轮出题时写全，漏掉的只能等下一轮；
4c. 每道主问必须留兜底出口（模板自动追加，出题者不得删）；
5. 新增**禁用措辞表**一节；
6. 记录**为什么不借鉴 grill-me 的"每题推荐答案"**——这是本 skill 与通用 grilling 类技能的分界。

**`spec-template.md`**（新增段落）

- `## 被否决的口径及理由`：业务选了 A，则 B／C 连同选项里写的代价（"多约 1.5 天开发"、"分子分母不是同一批单，可能超过 100%"）一起落入。解决"半年后有人再提同一方案，翻不到当初为什么不行"。由 build/回执解析自动产出，零人工成本。

**`references/blindspot-checklist.md`**

- 每个维度补一句"怎么判它适用／不适用"的可执行判据（借 `codebase-design` 的 deletion test 写法）。

## 10. 测试与验证

- `tests/` 新增场景，四种成色各一份 HTML 回执样本 → 跑 `check_questionnaire.py` 断言退出码与告警条目：①全填署名（0 WARN 0 FAIL）②未署名（WARN + 降级）③含证伪题（单独计数）④含未说明的矛盾（FAIL）。
- `build_questionnaire.py` 单测：悬空 `when` 引用、反向 `layer` 依赖、**分支覆盖空洞**（某选项选下去无题可问且未标终止）、`advice_allowed:false` 却带建议措辞 → 四种均应报错拒绝出包。
- 原型已验证过的行为（不必重测，作为实现验收基线）：现有 checker 零改动通过；`carry` 四态（自动带出／手改不覆盖／上游变更不覆盖已改／清空后重新接管）；`na` 与 `clash` 均正确落入回执。

## 11. 已知缺口与风险

| 项 | 说明 |
|---|---|
| 非文件证据引用 | `verify_evidence.py` 校验不了，见 §9 处置 |
| 未署名绕过机检 | 规则 1 未实装前，纪律有静默失效窗口 |
| 微信内置浏览器 | 会吞掉 `<a download>`，故必须保留「复制全文」按钮 |
| 打印保真 | 已有 print 样式（展开条件块、隐藏进度条与索引），未在真实打印机验证 |
| 视觉未截图确认 | 浏览器面板在设计期处于收起状态，样式仅由人工目视 |
| 题型受模板约束 | 单选／多选／文本／表格四种；新题型需改模板 |
| 未预见的分支只能进下一轮 | 通路无 AI 常驻，兜底出口只能收集"实际是什么"，不能当场追问；`kind:"other"` 的作答即下一轮的输入 |
